# Security audit, October 2026 (#157)

This audit reviewed the whole app: the webview, the Tauri adapter, the core,
plugins and themes, the installer, integrations and the release pipeline.
It looked for vulnerabilities that can be exploited. It lowers the risk but
cannot show that none remain. The [residual risks](#residual-risks) are part
of the result.

## Scope

- **Audited commit:** `b2cad34` (master, 2026-10-28).
  - The working tree already held the work that landed afterwards as
    `06e849c` (web games) and `c084e5c` (accounts, permissions, system
    statistics, notifications), so that work was reviewed too.
  - Uncommitted installer-resilience work (`crates/caskade-installer`,
    `caskade-core/src/install/`) was read as it stood.
- **Version:** 0.1.0, not yet released.
- **Platforms:**
  - Linux (x86_64): code reviewed, and Linux-only paths were followed
    (Wine/Proton, Flatpak, AppIndicator, xdg-open).
  - Windows and macOS: code reviewed only.
    - The reviewed paths are the `cfg(windows)` and `cfg(target_os = "macos")`
      branches: `rundll32`/`explorer` launches, NSIS/MSI/Inno, dmg/pkg and
      Gatekeeper.
    - Nothing was run on Windows or macOS.
- **Modes:** desktop and console. The install confirmation and plugin
  review are the same components in both shells. The install confirmation
  is mounted once, above both shells, in `main.tsx`. In both modes the core
  enforces the confirmation through the request id
  (`confirm_install_request`), whatever the UI does.
- **Not covered:**
  - live runs on Windows and macOS
  - fuzzing beyond the installer's existing fuzz targets
  - the caskade-server service itself (closed source)
  - third-party emulators, games and installers, which are trusted code
    once run (see the [threat model](#threat-model))
  - the Gitea runner hosts
  - the OS keychains

## Threat model

### Assets

- The user's files and accounts.
- RomM credentials in the OS keychain.
- The library database.
- The updater signing key.
- Integrity of what Caskade runs: games, emulators, installers and updates.

### Trust boundaries and attacker-controlled inputs

| Boundary | Untrusted input | Main controls |
|---|---|---|
| Web pages → `caskade://` deep links | `?url=` / `?path=` | Only queued; nothing is fetched or run until the user confirms by request id. The Install permission is checked. |
| Desktop → file drops, pasted text | Paths, shortcuts, URLs | The same confirmation queue. Shortcuts are resolved to a plan the dialog shows. |
| Webview ↔ adapter (IPC) | Command arguments | One capability (main window only), no fs/shell/opener plugins, a strict CSP (scripts from the app and `caskade-plugin:` only, `connect-src` IPC only), and a permission check on each command (unlisted commands are admin-only). |
| Custom schemes | `caskade-asset://`, `caskade-theme://`, `caskade-plugin://` paths | Decoded once, segment checks, symlink and canonical-path confinement, `nosniff`. HTML and SVG are never served as active content. |
| Archives and installers | Entry names, links, modes, sizes, programs | `SafeDir` writes. A 7zz sidecar pinned by SHA-256. Ratio and size caps. Execution policy. |
| Network services | caskade-server (IGDB), Hasheous, GitHub, RomM, libretro buildbot, Dolphin's update endpoint, Flathub, the updater feed | rustls, size caps, redirect rules, minisign-signed app updates. |
| Plugin backends (wasm) | Everything a backend returns | wasmtime sandbox, WASI preopens, a network host allowlist, grants checked by every host function, time and memory limits. |
| UI plugins | JavaScript | **Trusted by design.** They run in the main webview with the app's access. This is disclosed when the plugin is installed. |
| Themes | CSS, tokens, assets | The theme lint refuses at-rules, remote and escaping `url()`s, `expression()`, `!important` and selectors naming the consent dialogs, and the CSP blocks remote loads. |
| Metadata | Titles, descriptions, image URLs from IGDB, RomM and web pages | Rendered as React text (no `dangerouslySetInnerHTML`). Images are decoded with limits. |
| Storage roots (USB drives, shares) | `.caskade` manifests, launch specs | Identity marker, path confinement. Running a game from a drive runs that drive's code. |

### Out of scope by design

Running a game, an emulator or a native installer runs that code as the
user. Caskade doesn't sandbox games. Its job is to run them only after the
user asks.

## Method and tools

- **Code review:** each boundary in the table above, end to end: Tauri
  config and capabilities, every command group, the scheme handlers, the
  deep-link and drop queue, installer extraction and execution, uninstall,
  move, update carry-over, launch and emulator templates, managed emulator
  setup, game and app updates, the plugin host and its grants, theme
  compile and lint, RomM, IGDB, Hasheous and artwork, accounts and
  permissions, and SQL construction.
- **Dependency audit:**
  - `cargo audit` 0.22.2 with the RustSec database of 2026-10-28: 945
    crates.
  - `pnpm audit --prod`: no known vulnerabilities.
- **Static search** across `crates/`, `apps/` and `packages/` (grep) for:
  - shells
  - `Command::new`
  - openers
  - `danger_accept_invalid_certs`
  - redirect policies
  - `AssertSqlSafe`
  - `dangerouslySetInnerHTML` / `innerHTML`
  - `unsafe`
  - `${{ github.event` in workflow `run:` steps
- **Adversarial checks:** crafted inputs traced through the code, then
  turned into regression tests. The tests cover:
  - percent-encoded traversal in download names
  - `..` versions
  - a RomM server id pointed at another address
  - a cross-host 307 on sign-in
  - a plugin resolver naming a loopback download
  - the existing adversarial installer suite (`crates/caskade-installer/tests/adversarial/`)
  - the scheme handlers' traversal tests (`plugin_scheme_tests.rs`, the
    asset tests)

  The coordinator runs the new tests as one consolidated validation.
- **Earlier work re-verified:**
  - **Installer safety (#6):** path sanitising, `create_new` writes,
    symlink and hardlink confinement, case-folded collisions, setuid
    stripping, bomb limits, the pinned sidecar and uninstall root identity
    all hold up. CSK-01, CSK-12 and CSK-13 were gaps; they are fixed.
  - **Plugin capabilities (#124):** grants are checked by every host
    function, the preopens confine file access, and host matching holds
    up. CSK-03, CSK-05 and CSK-07 were gaps; they are fixed.

## Findings

Severity follows the impact and preconditions within this threat model.
"Details withheld" marks a finding that is still open: its proof of concept
is shared privately and will be published once it is fixed.

### Verified protections (summary)

- **Webview:**
  - There is no `dangerouslySetInnerHTML`, `innerHTML` or `iframe`.
  - The Markdown renderer builds React elements and links only `http(s)`.
  - The CSP blocks inline and remote script, and remote image, font and
    connect sources.
  - The web game player is a separate process with no IPC.
- **Deep links, drops and pastes:**
  - Requests are inert until `confirm_install_request`.
  - Requests expire and the queue is capped.
  - UNC and device paths are refused before they touch the filesystem.
  - The Install permission is required.
  - The dialog focuses Dismiss by default in both modes.
- **Installer extraction:**
  - Absolute, drive, UNC, `..`, ADS and reserved names are refused.
  - Files are written `create_new`.
  - Symlinks and hardlinks are confined to the destination.
  - setuid and setgid bits are stripped.
  - Ratio (1000:1) and size (100 GiB) are capped.
  - The 7zz sidecar is pinned and its output re-imported through `SafeDir`.
- **Uninstall:**
  - The root identity and the manifest must match.
  - The game folder must be a single component.
- **Move and update:** they are symlink-safe.
- **Launch:**
  - No shell is used.
  - Arguments stay separate and variables never split them.
  - Managed paths are confined to the game folder.
  - The toolchain (Rust ≥ 1.94) includes the CVE-2024-24576 fix.
- **App updates:**
  - Minisign is required.
  - The endpoint override is build-time only.
  - Release CI checks the key id against the committed public key.
- **Network:**
  - rustls everywhere.
  - Response size caps on IGDB, RomM and Hasheous.
  - Image decoding is limited to 8192², 16 MP and 128 MiB.
  - RomM file names are reduced to single components.
  - BIOS targets come from Caskade's own definitions, with MD5 checks.
- **Secrets:**
  - RomM credentials are kept in the OS keychain only, never in SQLite or
    logs.
  - Errors strip URLs.
  - There is no diagnostics export.
- **SQL:** every formatted query interpolates only constants. Input is bound.
- **CI:**
  - Actions are pinned by SHA with `persist-credentials: false`.
  - `pull_request_target` jobs run only for same-repo PRs.
  - No event data is interpolated into `run:` steps.

## Residual risks

- Games, emulators and native installers run with the user's full rights.
  Caskade decides *when* they run, not what they can do.
- UI plugins run with the app's full access. Installing one is a trust
  decision.
- Local accounts and PINs are a household lock, not protection against
  someone with access to the OS account.
- Windows and macOS behaviour was reviewed but not exercised. Of their
  platform-specific findings, CSK-09 is fixed, and CSK-15 is fixed but not
  yet run on macOS.
- A local file or folder that is an installer runs it under the default
  execution policy (Allow) once the drop or paste is confirmed; downloads
  from a link ask first (CSK-02).
- The release workflow's split between building and signing (CSK-04) runs
  for the first time with the next tag. Signing trusts what the build legs
  produced.
- The open findings above are tracked as follow-up issues with owners, and
  each records a risk decision.
