# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Caskade is a cross-platform, multi-modal video game manager and launcher, written in Rust (see `README.md`).

## Git workflow

- Commit all work to the default branch, `master`, in the main checkout. Don't create branches or git worktrees. Several agents work in this checkout at once, and work kept off `master` drifts from theirs and has to be merged back later.
- Commit only the files you changed: `git add <paths>`, never `git add -A`, `git add .` or `git commit -a`. Other sessions' uncommitted changes share the working tree; leave them for their owners.
- `AGENTS.md` repeats these rules for other coding agents. Keep the two in step.

## Current state

## Commands

pnpm workspace (`apps/*`, `packages/*`), with `just` wrappers for each command:

- `pnpm install`: install dependencies.
- `just dev` / `pnpm tauri dev`: the desktop app with hot reload. Vite serves the UI at http://localhost:1420 (`strictPort`, so only one dev server can run).
- `just web` / `pnpm dev`: the UI alone in a browser. The sidebar shows "Browser preview" because there is no core; views use mock fixtures when started with `VITE_CASKADE_FIXTURES=1`.
- `pnpm typecheck`: `tsc --noEmit` in every package. TypeScript is 7.x. RTK's `tsc` filter misreads its output, so run it as `rtk proxy pnpm typecheck`.
- `pnpm lint`: `biome check .`. `pnpm format` applies fixes. Biome covers only the web projects: it ignores `docs/`, `vendor/`, `crates/`, `xtask/`, `scripts/`, `.gitea/`, Tauri's `gen/` and icons, and the generated bindings.
- `pnpm test`: Vitest (jsdom, Testing Library) in every package.
- `pnpm build`: typecheck and production build of the UI.
- Translations (`docs/translating.md`, `docs/localization.md`): `just i18n` extracts marked text into `locales/<domain>.pot` (`ui`, `app`, `core`) and merges it into each `locales/<lang>/<domain>.po` (needs GNU gettext); commit both with the change. `just i18n-check` (also in CI) fails on a stale template, a PO file `msgfmt --check` rejects or a translation that drops or changes a placeholder or tag, and prints each language's completion. `pnpm i18n:extract --add <lang>` starts a language; adding `locales/<lang>/*.po` is all it takes to ship one.

## Rust build speed

- The desktop adapter emits only an `rlib`: the app, bindings exporter and catalogue tool are Rust binaries. Do not reintroduce the Tauri mobile template's `staticlib`/`cdylib` outputs for this desktop-only crate.
- Dev builds use `debug = "line-tables-only"`, and dependencies have no debug info (root `Cargo.toml`). Backtraces still show file:line. For a debugger session, build with `CARGO_PROFILE_DEV_DEBUG=full`.
- `just build-timings` builds the desktop binaries with Cargo's HTML timing report. [Build performance](docs/build-performance.md) explains the CI scopes, nightly/opt-in bundles and how to measure a change without cleaning the shared target.
- Each crate's integration tests compile into one `it` binary: `autotests = false` plus `[[test]] name = "it"` in its `Cargo.toml`, and `tests/main.rs` declares each `tests/<file>.rs` as a module. A new test file needs a `mod <file>;` line in `main.rs`. Run one file with `cargo test -p <crate> --test it <file>::`; insta snapshots are named `it__<file>__<name>.snap`. A few binaries stay separate (installer `cli` and `performance`, discovery `performance`) because CI runs them by name. `tests/fixtures/support/mod.rs` is declared once in `main.rs` and imported with `use crate::fixtures;`.

## App build, lint and test

- Build: `flock /tmp/caskade-heavy.lock cargo build -p caskade-core -p caskade-desktop`.
- Lint: `flock /tmp/caskade-heavy.lock cargo clippy --workspace --all-targets -- -D warnings`; Windows cross: add `--target x86_64-pc-windows-gnu` with `-p caskade-core -p caskade-desktop`. The macOS cross gate cannot cover the app: bundled SQLite, `ring` and Tauri's `objc2` helpers are C builds that need the Apple SDK. `caskade-core --no-default-features` drops the `net` feature (reqwest).
- Test: `just test-app` (core and adapter tests, then Vitest), or `flock /tmp/caskade-heavy.lock cargo test -p caskade-core -p caskade-desktop`. Adapter tests run commands and events on Tauri's mock runtime.
- Bindings: `just bindings` regenerates `apps/desktop/src/api/bindings.ts` (tauri-specta; debug app starts refresh it too). The test `committed_bindings_are_current` fails when the committed file is stale. Add a command by writing it in `src-tauri/src/commands/<area>.rs` and registering it in `src-tauri/src/bindings.rs`. 64-bit times and sizes cross as numbers; 64-bit ids cross as strings.
- App bundle: `just build-app` (`pnpm tauri build --debug`: deb and AppImage under the cargo target dir). The first AppImage build downloads and runs linuxdeploy, which is slow.
- The core emits `tracing` events; the app logs with `RUST_LOG` (default `info`).
- WebKitGTK paints on the CPU on NVIDIA's proprietary driver under X11 (~15 fps fullscreen at 1440p). The app then restarts itself with `WEBKIT_FORCE_DMABUF_RENDERER=1 WEBKIT_DMABUF_RENDERER_FORCE_SHM=1` (`src-tauri/src/webkit.rs`), unless a `WEBKIT_*` renderer variable is already set. Where WebKit still paints on the CPU, the page gets `<html data-paint="cpu">` and the `paint-cpu` token set pauses ambient loops.
- Lost webviews (#3, `src-tauri/src/webview_recovery.rs`): on Windows, WebView2's `ProcessFailed` reloads the page when its renderer exits or stays unresponsive for 20 s, and restarts Caskade when the browser process exits (installers and Windows updates can close it under the app). Three reloads within 2 min become a restart; past two restarts within 10 min (counted in `<cache>/webview-restarts`, so across processes) a native dialog offers Restart or Quit. The game and video windows reload or close themselves. The COM calls live in `crates/caskade-webview2` (the adapter forbids `unsafe`). Linux and macOS report no failures yet. To try it, end the `msedgewebview2.exe` renderer or browser process whose parent is `caskade.exe`.
- App icon and logo: `src-tauri/icons/source.svg` is the master (glyph on a dark square). Rebuild with `convert -background none icons/source.svg PNG32:icons/source.png`, then `pnpm tauri icon src-tauri/icons/source.png -o /tmp/icons` and copy back only the files `icons/` already has (it also writes Android and iOS sets). The in-app logo and favicon, `public/caskade.svg`, is the same glyph without the square; change both together.
- Tray icon (`src-tauri/src/tray.rs`), on Windows, macOS and Linux: Show and Quit in its menu. On Windows a left click shows the window. On macOS a click opens the menu, the icon is a template image, and a Dock click shows a hidden window (`RunEvent::Reopen`). The icons are the app icon's glyph without its dark square: `icons/tray.png` and `icons/tray-template.png`, written by `python3 scripts/tray-icons.py` (Pillow) from `icons/source.png`. Whatever brings the window back (tray, second start, deep link, guide button) calls `main_window::raise`. When `core.general.onClose` is `tray` (the default), the close button hides the main window to it. A close in console mode, or Quit, closes the window for good, through console mode's restore and window-state's save. On Linux it is an AppIndicator loaded at run time from libayatana-appindicator3 (or libappindicator3). Without either the app runs without an icon and the close button quits. Indicators get no clicks, only the menu, and GNOME shows them only with the AppIndicator extension. A second `caskade` start shows the window. `pnpm tauri build` needs `libayatana-appindicator3-dev`: the CLI finds the library through pkg-config and adds it to the deb's dependencies and the AppImage.
- Gamepads (console mode, #146): `crates/caskade-input` reads pads with `gilrs` (libudev on Linux: `libudev-dev` to build) and normalizes them to `Action`s (`nav.*`, `confirm`, `back`, `tab.*`, `guide`, …). The adapter (`commands/input.rs`) emits them as `inputActionEvent` only while a Caskade window has focus, except `guide`. Tests drive it with `InputService::without_pads` + `inject`. `cargo test -p caskade-input` runs without hardware; its `--no-default-features` build has no gilrs. Never send synthetic input to the real desktop: live checks run under Xvfb.
- Console mode (#148–#153): `commands/console.rs` makes the main window fullscreen and back, and remembers the choice in `core.console` (`start`: `auto` (gamescope, or the last mode), `desktop` or `console`; `active`). It starts in console mode with `--console`, `CASKADE_CONSOLE=1` or the setting. Window-state never saves the fullscreen window. The end-to-end run drives the built app with a scripted pad (`src/e2e.rs`, the `e2e` feature): `pnpm build`, then `xvfb-run -a -s "-screen 0 1600x1000x24" dbus-run-session -- cargo test -p caskade-desktop --features e2e --test it console_e2e:: -- --ignored`. It rebuilds the shared `caskade` binary with the frontend embedded, so rebuild without the feature afterwards. Hardware checks are in `docs/console-native-checklist.md`.
- Hasheous dumps: `caskade_core::hasheous::Hasheous` downloads and indexes the [Hasheous](https://hasheous.org/index.html?page=dumps) data dumps the library needs (configured emulators' platforms via `ids.hasheous` in `platforms.toml`, Windows for PC games, Mac for native macOS games) under `<cache>/hasheous/`, in the background, and answers hash and title lookups offline. Tests serve dumps from wiremock.
- IGDB metadata: `caskade_core::igdb::Igdb` asks caskade-server (`igdb::BASE_URL`, on Railway; closed source, so never link to it) for games by IGDB id and caches every answer, not-found ids included, in `<cache>/igdb/games.sqlite`. An id it has an answer for is never fetched again, concurrent lookups of the same id share one request (lookups of other ids don't wait for it), and only `refresh` refetches (answers older than ten minutes); a failed refetch keeps the cached answer. A lookup answers what the cache has and lists ids it couldn't answer yet in `pending`; it fails only when the server failed and none of the ids are cached. A failed request pauses every request for a minute, or for the server's `Retry-After` (seconds, up to 6 h); an id the server leaves unanswered or sends unreadable waits 6 h. Responses may come gzipped (decoded in `igdb/fetch.rs`, not by reqwest's `gzip` feature, which would also decode the installer's downloads). Ids above `i64::MAX` are answered as not found without asking (they fail the server's whole batch). Tests serve the API from wiremock; `igdb::tests::live` (ignored) hits the real server. The app manages one `Igdb` (`<cache>/igdb/`) and exposes it as `igdb_games` / `igdb_refresh` / `igdb_search` (`commands/igdb.rs`, ids as strings; a search, the server's `POST /search` by title, always asks the server and caches the games it finds); the webview calls them through `nativeIgdbApi` in `src/api/igdb.ts`. Answers cached in an older game shape (`igdb/store.rs` `SHAPE`; 1 had no age ratings, 2 no videos; bump it only once the server sends the new fields, or the refetch caches games without them for good) still answer but are fetched again once by the next lookup that needs them; a failed refetch keeps them, and Metadata leaves such games pending until it comes. Games carry `ageRatings`; `igdb::age` maps each board's label to a minimum age (unrated = `None`), stored per library game in `games.age_ratings_json` / `games.min_age` (migration 0015; applied like the other fields, a merge takes the highest).
- Game videos: IGDB games carry `videos` (YouTube ids, from the server). Library game pages (`GameVideos`, from `game_igdb`'s cached game) and Store game pages show them (`views/game/Videos.tsx`, `api/videos.ts`), and the Store page shows IGDB's screenshots in the same gallery as the library's. YouTube's player refuses to play in the app's pages (error 153: `tauri://localhost` sends no web referrer), so `video_play` (`commands/video.rs`) opens the video window, `caskade --video <id>` (`src-tauri/src/video_player.rs`, plain tao + wry like the game window): the embed loaded with `Referer: https://dev.caskade.app/`, over the middle of Caskade's window or fullscreen in console mode, one at a time, closed by Escape, a pad's B or Guide, and when Caskade exits (it holds the window's stdin). The CSP allows images from `images.igdb.com` and `i.ytimg.com`.
- Store catalog (#163): `Igdb::catalog_search` / `catalog_recent` / `catalog_upcoming` / `catalog_filters` (the server's `/catalog/*`) keep pages in memory (5 min, 30 min, 1 day), share concurrent requests and answer the last copy, `stale`, when the server fails; `catalog_games` refetches answers older than a day. Commands `igdb_catalog_*` and `igdb_owned`; the webview's `CatalogApi` (`src/api/igdb.ts`, fixtures in `catalogFixtures.ts`). The Store (`views/StoreView.tsx`, state in `/store`'s URL) and a catalog game's page (`/store/games/$igdbId`, `views/store/`) create no library entries; `from` chains through catalog pages like game pages (`views/game/origin.ts`).
- Library IGDB matches: `caskade_core::metadata::Metadata` gives each library game an IGDB id (its RomM ROM's `igdb_id`, then a Hasheous name match in its platforms' dumps, then the server's `POST /match` for its store ids: Steam, GOG, Epic, …; IGDB knows Epic games by the offer the store sells them as, which `metadata/epic.rs` reads per namespace from Epic's public catalogue) and keeps it in `igdb_matches`. For RomM games IGDB comes second: RomM's sync brings the title, description, genres, release date, alternative names and cover (and its screenshots, up to 4), and replaces what IGDB filled in where RomM had nothing; IGDB adds the hero, icon, tags and whatever RomM leaves empty. Images only the game page shows (screenshots, the hero) download when the page first opens (`game_page_images`: `RommService::page_images`, then `Metadata::page_images`), not during syncs or matching. Applying a match fills the description, genres, tags, release date and aliases where the game's own value is empty or is what the last apply wrote, and adds IGDB's cover (unless the game has its own) and icon as `igdb:<image id>` artwork, then its hero and 4 screenshots when the page opens. `watch` runs at start, after scans and hourly; games without a match are looked up in the Hasheous dumps again when they change, and sent to `/match` again only after a week. A run stops at the server's first failure or once an image host can't be reached, and failed runs retry after 10 min, doubling (±20 % jitter) to 1 h while offline and to 6 h when the server answers without a usable game. Images download outside the lock that orders match changes, so Set, Rematch and Separate never wait for one. An image that can't come (404, not an image) leaves the game without it instead of pending; IGDB artwork of a kind stays until its replacement is stored, so a failed download never drops a cover. A matched id the server sends no game for stays pending; only IGDB's "not found" undoes an apply. Games that are one game merge into one, with an entry (and a Play button naming its platform) per release: the same IGDB id, or the same title released within 5 years, since IGDB gives many ports ids of their own and RomM leaves some releases without one (`LibraryStore::same_games`, after each run, offline too, and after a match by hand; a game without a match joins only by title and a known date, a matched one leads its group, and hidden games and those set to "not on IGDB" stay out). The game page's Separate (`game_separate_entry`) moves an entry out into a game of its own, listed in `kept_apart`, which is never merged again. The game page's IGDB panel (`views/game/IgdbPanel.tsx`) reads the match from the caches only (`game_igdb`) and changes it with `game_igdb_set` (an id, or `null` for "not on IGDB"; the panel searches by title, prefilled with the game's, or takes a typed id; an id also renames the game to IGDB's title, and its sort title unless the user set their own), `game_igdb_rematch` and `game_igdb_refresh`.
- App updates: `commands/app_update.rs` updates Caskade itself through `tauri-plugin-updater`. The feed is `latest.json` on the newest published GitHub release (`ENDPOINT`; a build overrides it with `CASKADE_UPDATER_ENDPOINT`), checked against the minisign public key in `tauri.conf.json` (`plugins.updater.pubkey`). The private key and its password are `~/.tauri/caskade-updater.key` and `.password`, never in the repo. The webview only asks to check, install and restart (`app_update_*`; the status follows `AppUpdateChanged`). AppImage, NSIS, MSI and the macOS app update in place; a deb or a dev build says why not (`unavailable`). While `core.appUpdates.check` is on and first-run setup is done, it checks 30 s after start and then every 6 h. Nothing downloads until the user presses Download and install (Settings → General → Caskade updates, or the status bar's link), and the new version runs after Restart now. `bundle.createUpdaterArtifacts` stays off in the committed config, so local and Gitea bundles need no key; the release workflow turns it on.
- Game updates: `caskade_core::updates` follows managed installs whose source an `UpdateProvider` knows. GitHub releases is the only one so far. `Tracker` records the project, release and file from the install's URLs and the file it downloaded (`Prepared::download_url`) in `game_updates`. Installs from before tracking, or whose URL names no release, count as the release that was newest at their first check. `Updates::watch` checks every `core.updates.intervalHours` (6 by default) without an API key: the `releases/latest` redirect, or `releases.atom` with prereleases on. Play calls `game_update_before_play`, which re-checks when the last check is more than an hour old. A failed check keeps the last answer and the time of the last check that worked, and the watch and Play leave that install alone for 30 min (managed emulators' checks too); the watch's round stops when the provider can't be reached. Updating (`InstallService::update_game`, job kind `update`) downloads first. It then sets the old folder aside in `<root>/.caskade/updates/<job>` and installs under the same folder name and `caskade-install` id. Files the user added or changed are carried over (`install/carry.rs`); where upstream changed the same file, the user's copy goes to `.caskade/update-backup/<old version>/`. Then the old folder is deleted. A failed update puts the old folder back, and `recover_updates` finishes or undoes interrupted ones at startup. When the API is rate-limited (403/429), the installer's GitHub resolver falls back to the release page's `expanded_assets` list. `updates::tests::live` (ignored) hits github.com.

Providers (`net` feature) share `store_accounts::http`; Steam (#166, `steam.rs`) signs in with the user's Web API key and profile and imports `GetOwnedGames` (games only, played free games, play time when given; a private profile is `Unavailable`, never an empty library); `StoreAccounts::credentials` gives core features (achievements) an account's renewed sign-in without it leaving the core. GOG (#167, `gog.rs`): the pasted login-page address or code for Galaxy-client tokens (renewed), every `getFilteredProducts` page (games only, `worksOn` as `systems`); any failed page keeps the last library. Epic (#168, `epic.rs`): the pasted `authorizationCode` for launcher-client `eg1` tokens (renewed), every library page by cursor with catalogue bulk lookups (public `games` only: no add-ons, `ue` assets or private sandboxes), play time per app; owned and local Epic ids match on namespace + catalog item (`db/store_accounts.rs` `key`), so editions with one title stay apart. Play time (#169, `db/playtime.rs`, migration 0024): reported totals are `remote_playtime` rows per release/provider/account, never sessions; a game's time is its sessions plus each row's `counted_ms`, recounted per store-identity family (accounts add, a launcher's own total overlaps them, the largest total seen counts, sessions ended before the read are inside it); discovery seeds became launcher rows; `core.storeAccounts.playtimeImport` (never/newGames/always); `game_playtime` and `views/game/PlaytimeSources.tsx` show the sources. Installing owned games (#170, `store_accounts/install.rs`): `owned_releases` gives each owned release's state (installed, available, installing, launcher missing, unsupported system, unavailable); `install` opens the provider's launcher URI and waits for discovery to find the copy (never claimed); the Library's Ready to Install tab is `GameFilter::Owned`; the game page shows `views/game/OwnedReleases.tsx`.
- Installs: `caskade_core::install::InstallService` owns the job queues and maps finished installs into the library. In the app, deep links (`caskade://install?url=…` / `?path=…`, `src-tauri/src/deep_link.rs`), file drops and pasted input all land in the `InstallRequests` confirmation queue (`commands/install_requests.rs`). A drop on the library goes through `request_dropped_install` first: `caskade_core::install::dropped::plan` resolves a shortcut (`.lnk`, `.url`, `.desktop`) to its target and turns a game's own executable into its folder plus a launch hint, and the confirmation shows that plan. Nothing downloads or runs until `confirm_install_request`. Magnet links, `.torrent` files and HTTP(S) links to one install through the same pipeline (the installer's `torrent` feature, librqbit, turned on by core's `net`; see the installer README's Torrents section): nothing is seeded after a download, and a cancelled torrent keeps its verified pieces for Retry. Add game's menu names both (Install from file… takes a `.torrent`, Install from link… a magnet link). Settings → Installer's Magnet links and torrent files (`src-tauri/src/torrent_links.rs`, `torrent_links_*`) asks the OS to send them to Caskade: on Linux a `NoDisplay` `caskade-torrent-links.desktop` becomes the `x-scheme-handler/magnet` and `application/x-bittorrent` default, remembering the previous apps in `X-Caskade-Previous-*` keys, which turning it off restores; on Windows Caskade registers under HKCU (ProgIds, capabilities, `RegisteredApplications`) and opens Default apps, since only the user can choose; macOS isn't supported. The OS starts `caskade <magnet | .torrent path or URL>` (`torrent_links::input_from_args`, also in the single-instance callback), and it becomes an install request like a deep link (`deep_link::queue`). Debug builds register the `caskade:` scheme for the dev executable at startup. To try a link on Linux: `xdg-open 'caskade://install?path=/abs/path'`.

## Plugin host

`crates/caskade-plugin-host` reads `plugin.json` manifests, discovers plugin
folders and runs backend components in wasmtime against `wit/caskade-plugin.wit`
(`caskade:plugin@0.1.0`). Docs and the manifest JSON Schema are in `docs/plugins/`.

- Test: `flock /tmp/caskade-heavy.lock cargo test -p caskade-plugin-host`. The integration tests build the test guest (`tests/guest`, its own workspace) for `wasm32-wasip2`; install the target once with `rustup target add wasm32-wasip2`.
- `plugins/examples/caskade-pack` is an example plugin (an install handler and a URL resolver, #55); its `backend/` crate has its own workspace and lock. `tests/installer.rs` builds it and installs a pack from a local page with it.
- The manifest schema test fails when `docs/plugins/plugin.schema.json` is stale; regenerate it with `CASKADE_WRITE_SCHEMA=1 cargo test -p caskade-plugin-host`.
- Add-on catalogue (#181–#184, `docs/plugins/catalogue.md`, authors: `docs/plugins/publishing.md`): `caskade_core::addons` reads a signed (minisign, the updater's release key), validated catalogue of plugins and themes, cached for offline use, and works out each entry's compatibility on the device. `addons::package` downloads (size and SHA-256 checked), unpacks safely, checks the manifest and swaps an add-on in with a journal that rolls back on failure and at startup. Commands are in `commands/addons.rs` and `commands/addon_packages.rs`. A first plugin install needs the permission review; an update keeps the grants. The UI is `components/addons/` in Settings → Plugins, over `AddonsApi` (`api/addons.ts`, fixtures in `addonsFixtures.ts`). Tests point the app at a local catalogue with `CASKADE_CATALOGUE_URL` and `CASKADE_CATALOGUE_PUBKEY`. `caskade-catalogue` (a desktop bin over `addons::author` and `addon_tool.rs`) builds reproducible packages and the catalogue from a source file and checks a staged or published one as installs do; `just starter-catalogue` builds the starter collection (`scripts/addons/starter.json`: the playtime-stats and gamemode examples and the Ember theme; howlongtobeat is left out while howlongtobeat.com refuses its requests, `themes/ember`, which isn't built in). `commands/addon_smoke_tests.rs` runs build → sign → check → install → update → rollback against a local server.

## UI architecture (`apps/desktop/src`)

- `router.tsx`: TanStack Router routes, defined in code. View state lives in the URL through `validateSearch`: the Library filter and search query (`/library?filter=installed&q=survival`), the Store filter (`/store?filter=buy`) and the Settings tab plus an optional sub-section that the panel validates (`/settings?tab=emulators&section=scanners`).
- `shell/`: app shell (sidebar, topbar, `<Outlet>`). Sidebar entries are defined in `shell/nav.ts`; the Library's filters (Recently Played … All Games, with counts) are links under its entry (`NavItem.sub`, `shell/LibraryNav.tsx`), in both sidebars, sliding open only while the Library is open; the Library view keeps only its toolbar (Select, Add game, a platform's All platforms back link and a search's clear chip on the left; Save as collection, sort and layout on the right). The topbar search (`shell/SearchBox.tsx`) is a React Aria `ComboBox`: suggestions come from `searchGames` in `mocks/games.ts`, and Enter opens `/library?q=…`. It stays for the mouse and Ctrl K. Typing anywhere outside a text field, or `/`, opens `shell/TypeSearch.tsx`: a RetroArch-style centred overlay with only the text and the match count. In the Library it filters the games as it changes; elsewhere Enter opens the Library on the results. A pad types on the on-screen keyboard instead.
  - Console mode's shell is `shell/console/` (`ConsoleShell`, `ConsoleSidebar`, `ConsoleTopbar`, `HintBar`), chosen by `AppShell` from `useMode()` (`shell/console/mode.tsx`, which sets `<html data-mode>`). The `mode-console` token set (`packages/tokens/tokens/sets/`) raises the type scale, card and hero sizes and the focus ring. Views give a pad its first stop with `data-focus-default` and `useDefaultFocus`, and bind buttons with `useInputAction` (labels show in the hint bar; `global: true` keeps a binding inside menus and dialogs). The buttons mean the same on every view: A selects, B goes back or closes, X opens a card's quick look (`components/gameMenu/QuickLook.tsx`, where X again plays), Y searches, Start opens the focused item's menu, LB/RB switch the view's main tabs (`useScreenTabs`: Library filters, Settings tabs, Store and Collections filters, a game's plugin tabs; in place, not in history), LT/RT page the list focus is in (`ShelfRow`, the library grid, letter by letter when sorted by title) or else the view. A dialog that opens focused on itself moves a pad to its `data-focus-default` or first control. Text fields take a pad through the on-screen keyboard (`input/OnScreenKeyboard.tsx`): A on a field, Y for the search, or a tap in console mode opens it; focus stays in the field. Spatial navigation stays in the current area (sidebar or content) while it has a target that way, a target in the row or column focus is in beats one beside it, and a settings row is one stop going up and down. `src/test/harness.tsx` renders the whole app over fixture APIs with a fake pad (`renderApp`, `fakeLayout`), for action-only tests.
  - The main window has no native decorations (`decorations: false`; macOS keeps its traffic lights through an overlay title bar, `tauri.macos.conf.json`). The topbar is the title bar: `WindowControls` (minimize, maximize, close), and `data-window-drag` regions on the topbar, the sidebar brand and the status bar. `useWindowDrag` moves the window only once a press travels, so a double click reaches the page and maximizes. Don't use Tauri's `data-tauri-drag-region`: its grab on mousedown swallows double clicks on Linux. Edge and corner resizing is Tauri's native undecorated-resize handler. The window comes through `AppWindowContext` (`shell/appWindow.ts`); tests use `shell/windowFixture.ts`. Window-state does not restore `decorated`. The main window starts hidden (`"visible": false`, except on macOS) and setup shows it (`window_state::show`): tao maps a window before taking its decorations off, and Muffin and Mutter then report the title bar's frame extents for it, so every saved position was that much too high.
- `drop/`: files dropped from the desktop. `DropProvider` (in `main.tsx`) hit-tests Tauri's native drag position and hands the paths to the innermost `useDropZone` under the pointer, or to the fallback (`InstallIngress`, a plain install request). Any control that opens a file or folder picker should also be a drop zone. Tests drive it with `fakeDrops` (`drop/testing.ts`).
- Pickers: ask for a file or folder with `usePathPicker().pick(request, nativeFallback)` (`components/pathBrowser/`). Desktop mode runs the native dialog; console mode shows `FolderBrowser`, an in-app browser a pad drives (A opens or picks, B cancels, LB/RB places, LT/RT pages, Start picks the folder), over the core's `browse_dir`. `PathPickerProvider` sits inside each `InputProvider` (the shell, first-run setup). Tests give it a tree with `BrowseApiContext` + `createBrowseFixtureApi`.
- `views/`: one component per route. Settings tab panels live in `views/settings/` and are registered in `SettingsView`'s `panels` map. Tabs without a panel show a placeholder. A large panel keeps its parts in a subfolder, e.g. `views/settings/emulators/` (see EMULATION-PLAN §7). `components/`: app-only shared pieces (`CollectionCard`, `StoreLinks`, dialogs).
- `packages/ui` (`@caskade/ui`): the themeable components, imported by the app and shared with UI plugins through the import map.
  - Form primitives built on `react-aria-components`: `Button`, `Switch`, `Checkbox`, `Select`, `TextField`, `Slider`, `SegmentedControl`, plus `SettingsSection` / `SettingRow` / `StatusDot` / `Pill` for settings layouts.
  - Game pieces: `GameCard`, `GameArt`, `StatusBadge`, `Hero`, `Shelf`.
  - Menus: every dropdown is a React Aria `MenuTrigger` around `MenuPopover` + `Menu`, with `MenuItem` (icon, description, `tone="danger"`), `MenuSection` and `MenuSeparator`. A right-click menu is `ContextMenu` + `useContextMenu`: it opens at the pointer, or beside the element for the context menu key, Shift+F10, a pad's Start or an actions button. WebKit's own menu is off app-wide (`shell/nativeMenu.ts`), except in text fields and on selected text; debug builds show it on Shift+right click, for Inspect Element. A game's menu is one app-wide `GameMenuHost` (`components/gameMenu/`, in `AppShell`): `useGameMenu(target)` / `useGameMenus()` open it from a card, a hero, a search suggestion or an entry row (`entryId` scopes it to that entry). It plays or stops the game (the game page's update-then-launch flow, `views/game/launch.tsx`), opens its page, toggles the favourite (`set_game_favorite`), shows its folder (`reveal_game_entry`, which takes an entry id, never a path), moves, uninstalls or hides it, and runs plugins' `game.actions`; its dialogs live in the host, so a virtualized card can unmount. Choosing a game (`useSelectGame`: a click on a card, a list row or a search suggestion) opens its quick look as a panel on the right in desktop mode, where View more opens its page and a click elsewhere in the view, except on another game, closes it; console mode opens the page. A game page's `from` search param (`views/game/origin.ts`, validated to app pages) is where its Back link returns: the page it was opened from, back through the last 4 games opened from each other, else the Library. Other rows (jobs, settings lists, the title bar) offer their own buttons through `useActionMenus()` (`components/ActionMenu.tsx`).
  - The anatomy catalogue in `src/anatomy.ts` lists every component's root, parts and states, the shell's included. It generates `docs/theming/anatomy.md` (`pnpm --filter @caskade/ui docs`).
  - Tests render each catalogued component and fail on an undocumented `data-part` or state value. The app's `src/anatomy.test.tsx` covers the shell. A selector lint fails on class selectors in the app's or the package's CSS.
  - The app's Tailwind scans the package through `@source` in `styles/index.css`.
  - Style interaction state with React Aria's data attributes (`data-selected:`, `data-hovered:`, `data-focus-visible:`, `group-data-*`), not `:hover`/`:checked`.
  - A control placed inside a `SettingRow` is labelled by the row through React Aria contexts, so it needs no label of its own. Give a second control in the same row an `aria-label`.
  - Do not add translate classes to `SliderThumb`. React Aria already positions it with `translate(-50%, -50%)`.
- `mocks/games.ts`: placeholder data. `GameArt` draws gradients until real artwork exists. All of this is replaced by typed Tauri commands later.
- `styles/`: the theming contract from TECH-PLAN §5, set up from the start:
  - `index.css` declares the cascade layer order (`cs.reset … cs.user`) and imports Tailwind's pieces into those layers.
  - The `--cs-*` design tokens are DTCG JSON in `packages/tokens/tokens/` (`@caskade/tokens`), compiled to `packages/tokens/tokens.css` by `pnpm --filter @caskade/tokens build`. `index.css` imports that file into `cs.tokens`. Edit the JSON, never the CSS. A test fails on any `--cs-*` the contract doesn't declare. See `docs/theming/README.md`.
  - `@theme inline` maps the tokens to Tailwind utilities (`bg-surface-raised`, `text-fg-muted`, `rounded-card`, …).
  - Always style through these token utilities, not raw colours.
  - Put `data-cs` / `data-part` / `data-status` attributes on components so themes can target them, and add new ones to the anatomy catalogue. Class names are not public API.
  - The sci-fi accents and motion are theme material: they live in `themes/default/theme.css` (the built-in `caskade.default` theme, #139). That covers the backdrop grid, HUD corner brackets on `data-cs="hero"`/`"panel"`, hero scanlines, card hover glow and sweep, and the active-nav rail. The app applies the theme's compiled stylesheet before the first render (`src/themes/apply.ts`); without the core, the browser preview inlines it. `base.css` keeps the `cs-enter` keyframes that `animate-enter` needs.
  - Motion:
    - Durations come from `--cs-motion-*` tokens.
    - Looping animations set `animation-play-state: var(--cs-motion-ambient)`.
    - `prefers-reduced-motion` zeroes both of these through the `reduced-motion` token set (`packages/tokens/tokens/sets/`). Follow the same pattern for any new animation.
  - Enter animations: use `animate-enter` and set `--i` (inline style or `[--i:n]`) to stagger siblings. The delay is built into `animate-enter`, because the `animation` shorthand would reset a separate `animation-delay`.
  - `chamfer` is a utility that cuts the corners off an element. A glow on a chamfered element needs `filter: drop-shadow` on a wrapper, because the clip also cuts off `box-shadow`.
  - Fonts are bundled through `@fontsource-variable` (Oxanium for display, JetBrains Mono for data and labels, Inter for body text), so the app needs no network fonts.

## Installer build, lint and test

The standalone `caskade-installer` library lives in `crates/caskade-installer`.
It has no Tauri or other Caskade dependencies. Format features describe payload
families on every host; defaults enable every feature except the dev CLI.

All Cargo build/clippy/test/run commands share the machine's heavy lane:

- Build: `flock /tmp/caskade-heavy.lock cargo build -p caskade-installer --all-features`.
- Lint: `flock /tmp/caskade-heavy.lock cargo clippy -p caskade-installer --all-features -- -D warnings`.
- Test: `just test-installer` or `flock /tmp/caskade-heavy.lock cargo test -p caskade-installer --all-features`.
- Single test: `just test-installer test_name -- --exact` (include the module path for a unit test).
- Dev CLI: `flock /tmp/caskade-heavy.lock cargo run -p caskade-installer --features cli -- --help`.
- Isolated feature: `flock /tmp/caskade-heavy.lock cargo build -p caskade-installer --no-default-features --features windows-formats` (also `linux-formats`, `macos-formats`, `disc`, `fetch`, `cli`).
- Cross compilation lint: use the lint command above with `--target x86_64-pc-windows-gnu` or `--target x86_64-apple-darwin` before `-- -D warnings`.
- Format only this crate: `cargo fmt -p caskade-installer`.
- `just fixtures <args>`, `just fuzz <target> <args>` and `just corpus <args>` build fixtures, run a fuzz target and score the installer corpus.

The library emits `tracing` events and spans without setting a global subscriber.
Execution entry points carry job/handler identifiers; the CLI configures logging
with `RUST_LOG`. Avoid logging credentials and full URLs.

## Installer development CLI
